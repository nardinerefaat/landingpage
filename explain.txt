1.1 What this project does
--------------------------
Marketing-style site (“KingTech”) in the browser:

  • Hero with rotating headset images (Home).
  • Featured Products: search/filter, quantity, add to cart.
  • Shop By Category tabs (phones, laptops, audio, tablets, storage).
  • Three marketing pillars (file: testimonials.jsx — UI heading may say “Features”).
  • Footer with contacts.
  • Cart route `/cart`: line items, totals, clear, recommendations.

No real payment server — cart and catalogs are demo data in localStorage.

1.2 Main user flow
------------------
  A. Open "/" → loading text until catalogs are ready (see App.js).

  B. Main page stacks: Navbar → Home → Features → ProductCategory → Testimonials → Footer.

  C. Navbar: react-scroll jumps to sections (ids like home, features, …); React Router opens `/cart`;
     cart count comes from context. Theme toggle sets data-theme on <html>.

  D. Adding products: Features and ProductCategory call the same context function addToCart.

  E. "/cart": simpler NavbarCart + list + summary + recommendation cards.

1.3 Two kinds of navigation (why both exist)
-------------------------------------------
Inside navbar.jsx:
  • react-scroll `<Link>` = scroll inside the SAME page (anchors / section ids).
  • react-router-dom `<Link>` (often aliased `RouterLink`) = change route (e.g. /cart).

3.2 Catalog caching (why second visit feels fast)
-------------------------------------------------
useLocalStorage(key, []) reads localStorage synchronously on first paint, then writes back when state changes.

App.js runs a bootstrap effect that, if ALL five arrays already have items, skips fetching; otherwise fetch and set state.

[PATTERN NOTE] Dependency array nuances and eslint — your repo may intentionally relax rules for “run once” fetch; remember: what the effect closure sees on first run is whatever state was hydrated from storage that moment.

3.3 Cart storage (different pattern than catalogs)
-------------------------------------------------
Cart in DataContext: useState initializer reads localStorage "cart"; a useEffect writes JSON whenever cart changes.

Catalog slices: useLocalStorage hook.
Cart: manual get/set pair inside context.

Two valid patterns side by side — fine for learning; production teams often unify.

4.1 DataContext.js — THE CURRENT VERSION (study in this order)

(1) normalize(p)
----------------
Purpose: ONE place to unify product shape coming from DummyJSON vs your JSON mocks.

  image resolves in order (logical OR chain in code — first truthy wins):
    p.image || p.images?.[0] || p.thumbnail || ""

So laptops that use thumbnail, mobiles that use images[], etc., all become `.image` on allProducts rows.

Cart lines store whatever fields addToCart receives (Features passes image from images[0]).
Recommendation list uses normalized allProducts rows where .image is already set when possible.


(2) allProducts — useMemo
--------------------------
Combines five arrays from props `value`:
  ...(value?.products || []),
  ...(value?.mobileData || []),
  ... (+ audio, tablets, storage)
Then .map(normalize).

Dependency `[value]` only: whenever App passes a NEW object literal as `value`, this recomputes.
[ADVANCED HINT] That can happen every render of App unless you stabilize `value`.


(3) cart state + persistence
----------------------------
Lazy initializer parses "cart" from localStorage once.
Effect mirrors cart to storage on each update.


(4) addToCart(product)
----------------------
Functional setState:

  • find existing line by product.id → if found, quantity += incoming product.quantity
  • else spread [...prev, product]

So duplicate clicks merge quantities by id.


(5) handleQuantity(id, operation)
---------------------------------
  • "delete" → filter out id
  • "plus" / "minus" → map; minus uses Math.max(1, ...) so quantity never drops below 1 in logic

Cart UI (cart.jsx) also disables "-" when qty <= 1 — double safety + better UX.


(6) cartItemsCount
------------------
reduce sums (item.quantity || 0).


(7) clearCart  → setCart([])


(8) getRecommendations(currentProduct, products, cart = [])  ← YOUR NEW SIGNATURE
-----------------------------------------------------------------------------
Step A — bookkeeping:
  cartIds = Set of ids already in cart
  seen = Set to drop duplicate ids in recommendation candidates

Step B — filter candidates:
  • drop falsy rows
  • drop same id as currentProduct (don’t recommend the anchor item itself)
  • require p.image truthy [after normalize, blank string fails here]
  • drop anything already in cart
  • drop duplicate product ids via `seen`

Step C — scoring (same spirit as classic recommender demos):
  +3 same category
  +2 same brand
  + count of words from candidate title that appear as substrings inside anchor title

Step D — keep score > 0, sort high→low, take top 4.

ANCHOR RULE (cart.jsx):
    getRecommendations(cart[0], allProducts, cart)

So whatever product is FIRST in your cart drives similarity; reordering cart can change suggestions.
Third argument guarantees you don’t upsell duplicates of what’s already purchased in this session.


(9) Provider value
------------------
{ ...(value||{}), allProducts, cart, addToCart, handleQuantity, cartItemsCount, clearCart,
  getRecommendations }

Spreading App’s value injects catalogs + theme for consumers.


4.2 pages/cart.jsx — behaviors to rehearse aloud
-----------------------------------------------
• useMemo recommendations: empty cart → []; else three-arg getRecommendations.
• totalPrice useMemo: sum price * qty with guards.
• Empty state vs filled layout.
• Line items: +/- / delete wired to handleQuantity.
• Minus disabled when qty <= 1.
• Recommendation cards: fallback image URI if missing.
• addToCart({ ...item, quantity: 1 }) for “Add” on suggestion cards.
• Checkout button: no handler (placeholder).


4.3 features.jsx — deliberate naming trap (exam-style gotcha)
-------------------------------------------------------------
It destructures products, … from context but ALSO declares:

  const allProducts = showAll ? filteredProducts : filteredProducts.slice(0, 5)

That local variable is ONLY the slice of merged RAW lists used for rendering the grid/search.
It is NOT DataContext.allProducts (normalized merged list).

Cart and recommendations MUST use context’s allProducts; Features never reads that.

5.1 Why normalize belongs in Context
--------------------------------------
Without it, Laptop might expose `.thumbnail`, phone `.images`, and UI would scatter `?.[0]` checks.
Normalizer centralizes invariants on the merged recommendation/search catalog slice.

Residual brittleness: items that truly have NO image/thumbnail/url still become image="" and may disappear from getRecommendations’ filter.


5.2 Set-based exclusion in recommendations
------------------------------------------
cartIds and seen bring O(n) linear scans with cheap membership checks — good enough for toy catalogs.


5.3 Performance note — Provider value identity
----------------------------------------------
<DataProvider value={{ ... }}>
If App allocates a NEW object each render, `value` reference changes → allProducts useMemo recomputes
→ Consumers re-render. For small apps this is fine; at scale stabilize with useMemo/useCallback or split contexts.


5.4 Consistency checklist (where shapes can drift)
--------------------------------------------------
Features handleCart sends { id, image, title, price, quantity } — not normalized full object.

If someday you merge category into cart lines, ensure addToCart spread pattern still matches recommendation scoring fields.

5.5 Commented legacy getRecommendations
---------------------------------------
Your file retains an older scoring block commented out — useful Git history locally; decide later if deleting comments clarifies studying.
